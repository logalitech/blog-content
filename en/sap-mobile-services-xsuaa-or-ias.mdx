Almost everything in the SAP Mobile Services cockpit can be changed after the fact. Token lifetimes, destinations, features, roles, the client configuration. You create an app, you get it wrong, you fix it.

There is one exception. When a mobile application is created you choose which service issues the token it runs on, either XSUAA or Identity Authentication, and that answer is fixed for the life of the app.

SAP states it plainly in [the documentation](https://help.sap.com/doc/f53c64b93e5140918d676b927a3cd65b/Cloud/en-US/docs-en/guides/features/security/admin/config.html): **an app configured with XSUAA cannot be migrated to IAS, and the only way to change it is to create the application again.**

## What you are actually choosing between

XSUAA is the authorization service that comes with the BTP subaccount.

IAS is Identity Authentication, the identity service of the wider SAP landscape. Create an app with IAS support and Mobile Services hands the login over to the IAS tenant, then takes back a token that says who the person is.

That reads like a drawback, but it really isn't. It is how single sign-on works. The user signs in once, against the same tenant that guards the other SAP applications connected to it, with whatever the security team has put in front of it: the corporate user store, multifactor authentication, conditional access.

For more on how single sign-on works, see ByteByteGo's [What Is Single Sign-on (SSO)? How It Works](https://youtu.be/O1cRJWYF-g4).

## Choosing

IAS is the right answer when the organisation already runs an IAS tenant and expects one login across its SAP applications.

Decide it deliberately. It is the one setting you do not get to revisit.
