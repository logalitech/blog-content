Most settings of an app in the SAP Mobile Services cockpit can be changed after it is created: token lifetimes, destinations, features, roles, the client configuration.

A few cannot. One of them is made when the app is created: which service issues the token the app runs on, XSUAA or Identity Authentication (IAS). SAP's documentation is explicit: **IAS is only supported for new mobile apps, an app configured with XSUAA cannot be migrated to IAS, and the only way to change it is to create the app again.**

## The screen where it happens

## What differs between the two

|                     | XSUAA                                                                                                            | IAS                                                                                  |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Token issued by     | the authorization service of the BTP subaccount                                                                  | the IAS tenant, through OpenID Connect                                               |
| Available when      | always; it is the default                                                                                        | only if trust has been established between the subaccount and the IAS tenant         |
| Who may use the app | a BTP role collection that holds the app's role, assigned to users or mapped to a group of the identity provider | a group named `SAPMS_<role>` in the IAS tenant, which the customer creates and fills |
| Corporate login     | through the subaccount's trust configuration, which can point to IAS                                             | directly through IAS, which can forward the login to a corporate identity provider   |

With XSUAA, users can still sign in through IAS: the subaccount sends them to the same IAS login page, and XSUAA issues the token afterwards. So one corporate login is possible with either option.

The difference that remains is where access to the app is managed: role collections in the BTP cockpit, or groups in the IAS tenant. The `SAPMS_` group is not created by Mobile Services. If the app requires a role and nobody creates the group in IAS, every user is refused.

## Before choosing IAS

SAP's documentation says that the IAS default configuration "is not optimal for many mobile app use cases". By default a user can have one session. Each device counts as a session, so when the same user signs in on a second device, IAS invalidates the refresh token of the first one, and that device has to sign in again once its current token expires. If users work on a phone and a tablet, raise the session limit in the IAS settings before go-live. The maximum is 10.

An IAS based app also cannot revoke a user's tokens from Mobile Services.

## Choosing

Decide it before step three of the wizard:

- Which team administers access: role collections in the BTP cockpit, or groups in the IAS tenant.
- Whether the subaccount already trusts an IAS tenant. Without that trust, the wizard offers only XSUAA.
- With IAS, how many devices each user signs in on, so that the session limit is set before go-live.

Changing the answer later means creating a new app and moving the users to it.
